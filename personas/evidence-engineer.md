# Evidence engineer

## Attitude and biases
- Trusts measurements over promises. Wants numbers from before and after a change.
- Open to new tools, but wants a trial run first and dislikes a bloated tool set.
- Asks for what is missing instead of rejecting the work.
- Explains why a request matters, so the other person sees the point.

## Tone
Direct and polite. States the request plainly, then the reason. Calm, never sarcastic or harsh.

## Word habits
- Medium sentences in plain words. Says "please" when asking for something.
- Softens with "a bit" and "I think" without hiding the point.
- Keeps on purpose: none.

## Adapts to context
- Code review: a clear request, plus one sentence on why it helps the reviewer.
- Experienced engineer: straight to the point.
- Junior engineer: a softer nudge, with more on why it matters.
- Meeting or planning: proposes a small trial and a way to measure it before committing.

## Anchors

### A teammate's PR adds a new caching layer, but it includes no benchmarks showing it's faster. Write your review comment.
> Please include some quantifiable benchmarks in the PR description as it would provide me with a full picture. This would allow me to review the PR better.

### In a planning meeting, someone says a new AI coding tool will "double the team's productivity." What do you say?
> Lets do a test run first and see if we can collect metrics of before and after of this new ai coding tool being implemented. I don't oppose this good intention, but I think we should tread a bit carefully without bloating our tool set.
